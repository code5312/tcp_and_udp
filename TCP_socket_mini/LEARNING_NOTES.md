# 학습 노트 — TCP 소켓 미니 매칭 서버

단계별로 헷갈렸던 부분 / 버그 / 왜 그런지 정리.

## 1단계: 단일 클라이언트 에코 서버

### 버퍼가 정확히 꽉 찼을 때 널 종료(`'\0'`) 보장 안 됨
- **증상**: `read(client_fd, buffer, sizeof(buffer))`로 받은 데이터를 `cout << buffer`로 출력.
  `n`이 `BUFFER_SIZE`와 정확히 같아지면(버퍼를 정확히 꽉 채워서 수신) 배열 범위 밖을 읽는 UB 발생 가능.
- **원인**: `read()`는 정확히 요청한 바이트 수만큼만 채워줄 뿐, 널 종료 문자를 붙여주지 않음.
  이전에 `memset`으로 0을 채워놨던 덕분에 `n < BUFFER_SIZE`일 때는 우연히 안전했던 것.
- **왜 테스트로는 잘 안 드러나는지**: `nc`로 손으로 입력하는 짧은 문자열은 버퍼 크기(1024바이트)를 거의 채우지 못하기 때문.
- **해결 방향 (택 1)**:
  1. `read()`에 `sizeof(buffer) - 1`을 넘겨서 항상 한 자리 남기고, 읽은 직후 `buffer[n] = '\0'` 명시적으로 설정.
  2. 애초에 C 문자열처럼 취급하지 않고, 정확히 `n`바이트만 출력/처리하도록 작성 (널 종료에 의존 안 함).

## 2단계: 멀티 클라이언트 (select 기반)

### 왜 필요한가
- 1단계는 `accept()` 한 번 → 그 클라이언트와만 `read/write` 반복. 두 번째 클라이언트가 붙으려 해도 `listen` 큐에서 대기만 할 뿐, 첫 번째 클라이언트가 연결을 끊기 전까진 `accept()`가 다시 호출되지 않음.
- "매칭 서버"가 되려면 여러 클라이언트를 동시에 받아야 하므로, blocking I/O를 순차 처리하는 대신 **I/O 멀티플렉싱**(`select`)으로 여러 fd를 한 번에 감시해야 함.

### select() 사용 시 헷갈렸던 점
- **`fd_set`은 호출할 때마다 다시 채워야 함**: `select()`는 인자로 받은 `fd_set`을 "준비된 fd만 남기고" 덮어써버림. 그래서 루프 맨 앞에서 매번 `FD_ZERO` + `FD_SET`으로 감시 대상(listen_fd + 모든 client_fd)을 다시 채워야 함. 한 번만 세팅하고 재사용하면 두 번째 루프부터 대부분의 fd가 감시 목록에서 빠짐.
- **`max_fd + 1`을 넘겨야 함**: `select(nfds, ...)`의 `nfds`는 "감시하는 fd 중 가장 큰 값 + 1". 빠뜨리면 큰 fd 번호를 가진 클라이언트는 실제로 감시되지 않음(리눅스에서 조용히 무시될 수 있음).
- **연결 종료 시 벡터에서 안전하게 제거**: `vector<int> clients`를 순회하며 끊긴 fd를 `erase()`할 때 인덱스를 `++i` 하지 않고 그대로 둬야 다음 원소를 건너뛰지 않음(`erase` 후 뒤 원소들이 한 칸씩 당겨지므로).
- **listen_fd와 client_fd를 같은 방식으로 취급**: `FD_ISSET(listen_fd, ...)`이면 "새 연결 도착", `FD_ISSET(client_fd, ...)`이면 "데이터 도착 또는 연결 종료(`read`가 0 반환)"로 구분해서 처리.

### 검증
- 두 클라이언트를 거의 동시에 연결해서 각각 다른 메시지를 보낸 뒤, 서로 메시지가 섞이지 않고 자기가 보낸 메시지만 에코되는 것을 확인함 (`select`가 fd별로 독립적으로 read/write 하기 때문).

### 다음 단계 후보
- `select`는 fd 개수가 많아지면 `FD_SETSIZE`(보통 1024) 한계, 매번 fd_set 재구성/스캔 비용 등의 한계가 있음 → 이후 `poll`/`epoll`로 옮겨갈 수 있음.
- 지금은 "받은 걸 그대로 자기한테 에코"만 함. 실제 매칭 서버가 되려면 대기 중인 클라이언트 2명을 짝지어서 서로의 메시지를 상대방에게 전달(relay)하는 로직이 필요함.

### 다음 후보 중 어떤 걸 먼저 할지 결정: 매칭/relay 로직 선택 (poll/epoll 전환 대신)
- **이유 (게임 프로그래밍 관점)**: `select`→`poll`/`epoll` 전환은 "동접자가 많아졌을 때 얼마나 효율적으로 감시하느냐"는 백엔드 확장성 문제라, 실제로 수만 동접 트래픽을 다룰 때 의미가 커짐. 반면 "두 플레이어를 짝지어서 서로의 메시지를 주고받게 하는 relay 구조"는 실시간 대전 게임(핑퐁, 격투, 턴제 등) 서버의 핵심 뼈대 그 자체라서, 게임 서버를 공부하는 목적에 더 직결됨.
- **트레이드오프**: poll/epoll을 안 해보면 "왜 select가 프로덕션에서 잘 안 쓰이는지"는 나중에 다시 배워야 함. 지금은 relay(매칭)부터 만들고, 이후 동접자가 늘어나는 상황을 체감할 때 epoll로 넘어가기로 함.

## 3단계: 매칭(페어링) + relay

### 설계
- 접속한 클라이언트 중 짝이 없는 한 명을 `waiting_fd`로 대기시킴.
- 새 클라이언트가 붙었을 때 `waiting_fd`가 있으면 즉시 매칭 성사 → `map<int,int> partner`에 서로의 fd를 양방향으로 기록.
- 매칭된 클라이언트가 보낸 메시지는 자기 자신에게 에코하지 않고, `partner[fd]`로 그대로 relay.
- 아직 매칭 안 된(대기 중인) 클라이언트가 보낸 메시지는 무시(또는 안내만).
- 매칭된 두 명 중 한쪽이 연결을 끊으면: 남은 한쪽에게 "상대방이 나갔습니다" 알리고, `partner` 맵에서 양쪽 다 제거한 뒤 남은 쪽을 다시 `waiting_fd`로 돌려보냄(대기열 재진입).

### 검증
- 클라이언트 A 접속 → 대기. 클라이언트 B 접속 → 즉시 매칭, 양쪽에 매칭 완료 알림. A가 보낸 메시지가 B에게만 전달되고 A 자신에게는 안 옴(relay 확인). A가 연결을 끊으면 B에게 "상대방이 나갔습니다" 전달되고, B는 다시 대기 상태로 전환되어 새로운 클라이언트 C와 매칭됨을 확인.

### 구현 중 발견한 함정: `waiting_fd` 변수 하나로는 부족함
- 처음엔 대기자를 정수 변수 하나(`int waiting_fd = -1`)로만 관리하려 했음.
- 하지만 "A-B가 매칭된 상태에서 C가 접속해 혼자 대기 중일 때, A가 나가서 B가 다시 대기자가 되는" 상황을 생각해보면: `waiting_fd`에 B를 덮어쓰는 순간 기존에 대기 중이던 C의 자리가 사라져서 C는 영영 매칭이 안 됨.
- 실제로 버그를 만들어서 재현하기 전에, 큐 대신 변수 하나를 쓰면 안 되는 이유를 먼저 추론해서 찾아냄 → `int waiting_fd`를 `deque<int> waiting_queue`로 바꾸고, 대기열에 2명 이상 쌓이면 앞에서부터 짝짓는 `tryMatch()` 헬퍼로 교체.
- **교훈**: "동시에 최대 1명만 대기한다"는 가정은 매칭이 깨지고 재대기하는 경로가 생기는 순간 깨질 수 있음. 상태를 단일 변수로 표현할 때는 "이 상태가 될 수 있는 경로가 정말 하나뿐인가"를 항상 의심해봐야 함.

### 테스트 방법 (파이썬 → C++ 클라이언트로 전환)
- 처음엔 파이썬 `socket` 스크립트(`test_match.py`)로 검증했다가, "이 프로젝트 자체가 C++ 소켓 학습인데 왜 테스트를 파이썬으로 하냐"는 지적을 받고 C++ 클라이언트(`client.cpp`)로 교체함.
- 파이썬을 처음 골랐던 이유는 순수 편의성(타임아웃 기반 recv, 컴파일 불필요)이었을 뿐, C++로 못 할 이유는 없었음 — 오히려 클라이언트 쪽 `connect()` 흐름도 서버와는 다른 학습 포인트라 C++로 만드는 게 더 맞음.

## 4단계: C++ 클라이언트 (`client.cpp`)

### 설계
- `socket()` → `connect()`(서버와 달리 클라이언트는 능동적으로 연결을 시도) → 이후 표준입력(키보드)과 소켓을 **select()로 동시에 감시**하는 루프.
  - 소켓이 준비됨: 서버(혹은 relay된 상대방)로부터 메시지 도착 → 화면에 출력.
  - 표준입력이 준비됨: 사용자가 입력함 → 그대로 서버로 전송.
- 서버 쪽에서 배운 select() 패턴(fd_set 매번 재구성, `nfds = max_fd+1`)이 클라이언트에도 그대로 적용됨 — "여러 입출력 소스를 동시에 기다려야 하면 select"라는 게 서버/클라이언트 어느 쪽에도 통하는 일반적인 패턴이라는 걸 체감함.
- 표준입력에서 `read()`가 0을 반환하면(Ctrl+D, 즉 EOF) 연결을 정상적으로 끊고 종료.

### 검증
- 서버 + 클라이언트 A/B/C를 서브프로세스로 띄워 stdin에 실제로 문자열을 흘려보내는 방식으로 end-to-end 테스트: A 대기 → B 접속(매칭 성사 메시지 양쪽 수신) → A가 보낸 메시지가 B에게만 relay(A 자신에겐 안 옴) → B가 보낸 메시지가 A에게 relay → A의 stdin을 닫아 연결 종료 → B가 "상대방이 나갔습니다" 수신 후 재대기 → C 접속 시 B와 재매칭 → C가 보낸 메시지가 B에게 relay. 전부 기대대로 동작함을 확인.

## 코드 재검토에서 발견한 이슈: SIGPIPE

### 문제
- `relay`를 하려면 매칭된 상대방 fd에 `write()`를 해야 하는데, 그 상대가 이미 죽은(연결이 끊긴) 소켓이면 리눅스 기본 동작상 `SIGPIPE` 시그널이 발생하고, 그 기본 처리는 **프로세스 즉시 종료**임.
- 즉, 클라이언트 한 명이 지저분하게 연결을 끊는 타이밍만 잘 맞으면 서버 전체(다른 모든 연결 포함)가 통째로 죽을 수 있는 잠재적 위험.

### 실제로 재현해봄
- B를 매칭시킨 뒤 `SO_LINGER{on, 0}`으로 강제 RST 종료시키고, 그 직후(sleep 없이) A가 메시지를 보내 서버가 죽은 B에게 write를 시도하도록 5번 유도해봄.
- 5번 다 서버가 죽지 않음 — 이 케이스에서는 리눅스가 `SIGPIPE` 대신 `ECONNRESET`을 반환했고, 기존의 `write() < 0` 체크(`perror`만 하고 계속 진행)가 이미 안전하게 처리하고 있었음.
- **결론**: 이번 타이밍/환경(RST + 루프백)에서는 못 터뜨렸지만, SIGPIPE 자체는 "이미 에러 난 소켓에 다시 write할 때"처럼 다른 조건에서 여전히 발생할 수 있는, 소켓 프로그래밍에서 잘 알려진 위험임. 재현 성공 여부와 무관하게 방어 비용이 거의 0이라 그냥 적용함.

### 해결
- `main()` 맨 앞에서 `signal(SIGPIPE, SIG_IGN);` 한 줄로 SIGPIPE 자체를 무시하도록 함. 이렇게 하면 죽은 소켓에 write해도 시그널로 죽는 대신 그냥 `write()`가 `-1`(errno=EPIPE)을 반환하고, 그건 원래 있던 에러 처리 코드가 그대로 처리함.
- 서버뿐 아니라 클라이언트(`client.cpp`)에도 동일하게 적용 (서버가 먼저 죽는 경우 클라이언트도 죽은 소켓에 쓸 수 있으므로).

## 5단계: select → epoll 전환

### 왜
- 앞서 미뤄뒀던 "select의 확장성 한계"를 직접 비교해보려고 진행. select는 매 루프마다 감시할 fd 전체를 `fd_set`에 다시 채워야 하고(`O(N)`), 커널도 매번 그 fd_set 전체를 스캔함(`O(N)`), 게다가 `FD_SETSIZE`(보통 1024) 이상은 감시 자체가 안 됨.
- epoll은 관심 있는 fd를 `epoll_ctl`로 커널에 한 번만 등록해두면, `epoll_wait`는 "준비된 fd만" 담긴 배열을 돌려줌 → 매번 전체를 다시 등록하거나 스캔할 필요가 없어서 연결 수가 많아져도 효율적.
- select 버전(`server.cpp`)은 그대로 남겨두고, epoll 버전을 `server_epoll.cpp`로 별도 작성해서 같은 매칭/relay 로직을 유지한 채 멀티플렉싱 방식만 직접 코드로 비교할 수 있게 함.

### select와 다르게 헷갈렸던 점
- **등록은 한 번, 감시는 계속**: `epoll_ctl(epoll_fd, EPOLL_CTL_ADD, fd, &ev)`로 관심 fd를 등록해두면 끝. select처럼 루프마다 `FD_ZERO`/`FD_SET`을 반복할 필요가 없음. 클라이언트가 새로 붙을 때만 `EPOLL_CTL_ADD`, 나갈 때는 `close()`만 해도 커널이 알아서 감시 목록에서 빼줌(명시적 `EPOLL_CTL_DEL`은 필수는 아니지만 커널 버전에 따라 dup된 fd 등 예외 케이스가 있어 안전하게 직접 해줌).
- **루프 구조 자체가 달라짐**: select는 "전체 클라이언트를 돌면서 `FD_ISSET`으로 준비됐는지 확인"하는 구조였는데, epoll은 `epoll_wait`가 돌려준 이벤트 배열(`n_ready`개)만 그대로 순회하면 됨 → 매칭 안 된 클라이언트, 대기 중인 클라이언트까지 매번 전부 훑을 필요가 없어짐.
- **`ev.data.fd`로 어떤 fd가 준비됐는지 구분**: select의 `FD_ISSET(fd, ...)` 대신, 이벤트 구조체의 `data.fd`(또는 `data.ptr`)로 어떤 소켓이 준비됐는지 알아냄.

### 검증
- 기존 select 버전과 동일한 A/B/C 매칭·relay·재매칭 시나리오를 `server_epoll` + `client` 조합으로 다시 검증하여 동일하게 동작함을 확인.
