# 학습 노트 — TCP 소켓 미니 매칭 서버

> 이 프로젝트가 전체적으로 왜 존재하는지(TCP·UDP를 함께 만든 이유, 디렉토리 구조, 빌드 방법)는 상위 [`../README.md`](../README.md)를 먼저 보세요. 이 문서는 TCP 구현을 단계별로 진행하며 헷갈렸던 부분 / 버그 / 왜 그런지를 기록한 상세 로그입니다.

## 1단계: 단일 클라이언트 에코 서버

### 버퍼가 정확히 꽉 찼을 때 널 종료(`'\0'`) 보장 안 됨
- **증상**: `read(client_fd, buffer, sizeof(buffer))`로 받은 데이터를 `cout << buffer`로 출력.
  `n`이 `BUFFER_SIZE`와 정확히 같아지면(버퍼를 정확히 꽉 채워서 수신) 배열 범위 밖을 읽는 UB 발생 가능.
- **원인**: `read()`는 정확히 요청한 바이트 수만큼만 채워줄 뿐, 널 종료 문자를 붙여주지 않음.
  이전에 `memset`으로 0을 채워놨던 덕분에 `n < BUFFER_SIZE`일 때는 우연히 안전했던 것.
- **왜 테스트로는 잘 안 드러나는지**: `nc`로 손으로 입력하는 짧은 문자열은 버퍼 크기(1024바이트)를 거의 채우지 못하기 때문.
- **해결 방향 (택 1)**:
  1. `read()`에 `sizeof(buffer) - 1`을 넘겨서 항상 한 자리 남기고, 읽은 직후 `buffer[n] = '\0'` 명시적으로 설정.
  2. 애초에 C 문자열처럼 취급하지 않고, 정확히 `n`바이트만 출력/처리하도록 작성 (널 종료에 의존 안 함).

## 2단계: 멀티 클라이언트 (select 기반)

### 왜 필요한가
- 1단계는 `accept()` 한 번 → 그 클라이언트와만 `read/write` 반복. 두 번째 클라이언트가 붙으려 해도 `listen` 큐에서 대기만 할 뿐, 첫 번째 클라이언트가 연결을 끊기 전까진 `accept()`가 다시 호출되지 않음.
- "매칭 서버"가 되려면 여러 클라이언트를 동시에 받아야 하므로, blocking I/O를 순차 처리하는 대신 **I/O 멀티플렉싱**(`select`)으로 여러 fd를 한 번에 감시해야 함.

### select() 사용 시 헷갈렸던 점
- **`fd_set`은 호출할 때마다 다시 채워야 함**: `select()`는 인자로 받은 `fd_set`을 "준비된 fd만 남기고" 덮어써버림. 그래서 루프 맨 앞에서 매번 `FD_ZERO` + `FD_SET`으로 감시 대상(listen_fd + 모든 client_fd)을 다시 채워야 함. 한 번만 세팅하고 재사용하면 두 번째 루프부터 대부분의 fd가 감시 목록에서 빠짐.
- **`max_fd + 1`을 넘겨야 함**: `select(nfds, ...)`의 `nfds`는 "감시하는 fd 중 가장 큰 값 + 1". 빠뜨리면 큰 fd 번호를 가진 클라이언트는 실제로 감시되지 않음(리눅스에서 조용히 무시될 수 있음).
- **연결 종료 시 벡터에서 안전하게 제거**: `vector<int> clients`를 순회하며 끊긴 fd를 `erase()`할 때 인덱스를 `++i` 하지 않고 그대로 둬야 다음 원소를 건너뛰지 않음(`erase` 후 뒤 원소들이 한 칸씩 당겨지므로).
- **listen_fd와 client_fd를 같은 방식으로 취급**: `FD_ISSET(listen_fd, ...)`이면 "새 연결 도착", `FD_ISSET(client_fd, ...)`이면 "데이터 도착 또는 연결 종료(`read`가 0 반환)"로 구분해서 처리.

### 검증
- 두 클라이언트를 거의 동시에 연결해서 각각 다른 메시지를 보낸 뒤, 서로 메시지가 섞이지 않고 자기가 보낸 메시지만 에코되는 것을 확인함 (`select`가 fd별로 독립적으로 read/write 하기 때문).

### 다음 단계 후보
- `select`는 fd 개수가 많아지면 `FD_SETSIZE`(보통 1024) 한계, 매번 fd_set 재구성/스캔 비용 등의 한계가 있음 → 이후 `poll`/`epoll`로 옮겨갈 수 있음.
- 지금은 "받은 걸 그대로 자기한테 에코"만 함. 실제 매칭 서버가 되려면 대기 중인 클라이언트 2명을 짝지어서 서로의 메시지를 상대방에게 전달(relay)하는 로직이 필요함.

### 다음 후보 중 어떤 걸 먼저 할지 결정: 매칭/relay 로직 선택 (poll/epoll 전환 대신)
- **이유 (게임 프로그래밍 관점)**: `select`→`poll`/`epoll` 전환은 "동접자가 많아졌을 때 얼마나 효율적으로 감시하느냐"는 백엔드 확장성 문제라, 실제로 수만 동접 트래픽을 다룰 때 의미가 커짐. 반면 "두 플레이어를 짝지어서 서로의 메시지를 주고받게 하는 relay 구조"는 실시간 대전 게임(핑퐁, 격투, 턴제 등) 서버의 핵심 뼈대 그 자체라서, 게임 서버를 공부하는 목적에 더 직결됨.
- **트레이드오프**: poll/epoll을 안 해보면 "왜 select가 프로덕션에서 잘 안 쓰이는지"는 나중에 다시 배워야 함. 지금은 relay(매칭)부터 만들고, 이후 동접자가 늘어나는 상황을 체감할 때 epoll로 넘어가기로 함.

## 3단계: 매칭(페어링) + relay

### 설계
- 접속한 클라이언트 중 짝이 없는 한 명을 `waiting_fd`로 대기시킴.
- 새 클라이언트가 붙었을 때 `waiting_fd`가 있으면 즉시 매칭 성사 → `map<int,int> partner`에 서로의 fd를 양방향으로 기록.
- 매칭된 클라이언트가 보낸 메시지는 자기 자신에게 에코하지 않고, `partner[fd]`로 그대로 relay.
- 아직 매칭 안 된(대기 중인) 클라이언트가 보낸 메시지는 무시(또는 안내만).
- 매칭된 두 명 중 한쪽이 연결을 끊으면: 남은 한쪽에게 "상대방이 나갔습니다" 알리고, `partner` 맵에서 양쪽 다 제거한 뒤 남은 쪽을 다시 `waiting_fd`로 돌려보냄(대기열 재진입).

### 검증
- 클라이언트 A 접속 → 대기. 클라이언트 B 접속 → 즉시 매칭, 양쪽에 매칭 완료 알림. A가 보낸 메시지가 B에게만 전달되고 A 자신에게는 안 옴(relay 확인). A가 연결을 끊으면 B에게 "상대방이 나갔습니다" 전달되고, B는 다시 대기 상태로 전환되어 새로운 클라이언트 C와 매칭됨을 확인.

### 구현 중 발견한 함정: `waiting_fd` 변수 하나로는 부족함
- 처음엔 대기자를 정수 변수 하나(`int waiting_fd = -1`)로만 관리하려 했음.
- 하지만 "A-B가 매칭된 상태에서 C가 접속해 혼자 대기 중일 때, A가 나가서 B가 다시 대기자가 되는" 상황을 생각해보면: `waiting_fd`에 B를 덮어쓰는 순간 기존에 대기 중이던 C의 자리가 사라져서 C는 영영 매칭이 안 됨.
- 실제로 버그를 만들어서 재현하기 전에, 큐 대신 변수 하나를 쓰면 안 되는 이유를 먼저 추론해서 찾아냄 → `int waiting_fd`를 `deque<int> waiting_queue`로 바꾸고, 대기열에 2명 이상 쌓이면 앞에서부터 짝짓는 `tryMatch()` 헬퍼로 교체.
- **교훈**: "동시에 최대 1명만 대기한다"는 가정은 매칭이 깨지고 재대기하는 경로가 생기는 순간 깨질 수 있음. 상태를 단일 변수로 표현할 때는 "이 상태가 될 수 있는 경로가 정말 하나뿐인가"를 항상 의심해봐야 함.

### 테스트 방법 (파이썬 → C++ 클라이언트로 전환)
- 처음엔 파이썬 `socket` 스크립트(`test_match.py`)로 검증했다가, "이 프로젝트 자체가 C++ 소켓 학습인데 왜 테스트를 파이썬으로 하냐"는 지적을 받고 C++ 클라이언트(`client.cpp`)로 교체함.
- 파이썬을 처음 골랐던 이유는 순수 편의성(타임아웃 기반 recv, 컴파일 불필요)이었을 뿐, C++로 못 할 이유는 없었음 — 오히려 클라이언트 쪽 `connect()` 흐름도 서버와는 다른 학습 포인트라 C++로 만드는 게 더 맞음.

## 4단계: C++ 클라이언트 (`client.cpp`)

### 설계
- `socket()` → `connect()`(서버와 달리 클라이언트는 능동적으로 연결을 시도) → 이후 표준입력(키보드)과 소켓을 **select()로 동시에 감시**하는 루프.
  - 소켓이 준비됨: 서버(혹은 relay된 상대방)로부터 메시지 도착 → 화면에 출력.
  - 표준입력이 준비됨: 사용자가 입력함 → 그대로 서버로 전송.
- 서버 쪽에서 배운 select() 패턴(fd_set 매번 재구성, `nfds = max_fd+1`)이 클라이언트에도 그대로 적용됨 — "여러 입출력 소스를 동시에 기다려야 하면 select"라는 게 서버/클라이언트 어느 쪽에도 통하는 일반적인 패턴이라는 걸 체감함.
- 표준입력에서 `read()`가 0을 반환하면(Ctrl+D, 즉 EOF) 연결을 정상적으로 끊고 종료.

### 검증
- 서버 + 클라이언트 A/B/C를 서브프로세스로 띄워 stdin에 실제로 문자열을 흘려보내는 방식으로 end-to-end 테스트: A 대기 → B 접속(매칭 성사 메시지 양쪽 수신) → A가 보낸 메시지가 B에게만 relay(A 자신에겐 안 옴) → B가 보낸 메시지가 A에게 relay → A의 stdin을 닫아 연결 종료 → B가 "상대방이 나갔습니다" 수신 후 재대기 → C 접속 시 B와 재매칭 → C가 보낸 메시지가 B에게 relay. 전부 기대대로 동작함을 확인.

## 코드 재검토에서 발견한 이슈: SIGPIPE

### 문제
- `relay`를 하려면 매칭된 상대방 fd에 `write()`를 해야 하는데, 그 상대가 이미 죽은(연결이 끊긴) 소켓이면 리눅스 기본 동작상 `SIGPIPE` 시그널이 발생하고, 그 기본 처리는 **프로세스 즉시 종료**임.
- 즉, 클라이언트 한 명이 지저분하게 연결을 끊는 타이밍만 잘 맞으면 서버 전체(다른 모든 연결 포함)가 통째로 죽을 수 있는 잠재적 위험.

### 실제로 재현해봄
- B를 매칭시킨 뒤 `SO_LINGER{on, 0}`으로 강제 RST 종료시키고, 그 직후(sleep 없이) A가 메시지를 보내 서버가 죽은 B에게 write를 시도하도록 5번 유도해봄.
- 5번 다 서버가 죽지 않음 — 이 케이스에서는 리눅스가 `SIGPIPE` 대신 `ECONNRESET`을 반환했고, 기존의 `write() < 0` 체크(`perror`만 하고 계속 진행)가 이미 안전하게 처리하고 있었음.
- **결론**: 이번 타이밍/환경(RST + 루프백)에서는 못 터뜨렸지만, SIGPIPE 자체는 "이미 에러 난 소켓에 다시 write할 때"처럼 다른 조건에서 여전히 발생할 수 있는, 소켓 프로그래밍에서 잘 알려진 위험임. 재현 성공 여부와 무관하게 방어 비용이 거의 0이라 그냥 적용함.

### 해결
- `main()` 맨 앞에서 `signal(SIGPIPE, SIG_IGN);` 한 줄로 SIGPIPE 자체를 무시하도록 함. 이렇게 하면 죽은 소켓에 write해도 시그널로 죽는 대신 그냥 `write()`가 `-1`(errno=EPIPE)을 반환하고, 그건 원래 있던 에러 처리 코드가 그대로 처리함.
- 서버뿐 아니라 클라이언트(`client.cpp`)에도 동일하게 적용 (서버가 먼저 죽는 경우 클라이언트도 죽은 소켓에 쓸 수 있으므로).

## 5단계: select → epoll 전환

### 왜
- 앞서 미뤄뒀던 "select의 확장성 한계"를 직접 비교해보려고 진행. select는 매 루프마다 감시할 fd 전체를 `fd_set`에 다시 채워야 하고(`O(N)`), 커널도 매번 그 fd_set 전체를 스캔함(`O(N)`), 게다가 `FD_SETSIZE`(보통 1024) 이상은 감시 자체가 안 됨.
- epoll은 관심 있는 fd를 `epoll_ctl`로 커널에 한 번만 등록해두면, `epoll_wait`는 "준비된 fd만" 담긴 배열을 돌려줌 → 매번 전체를 다시 등록하거나 스캔할 필요가 없어서 연결 수가 많아져도 효율적.
- select 버전(`server.cpp`)은 그대로 남겨두고, epoll 버전을 `server_epoll.cpp`로 별도 작성해서 같은 매칭/relay 로직을 유지한 채 멀티플렉싱 방식만 직접 코드로 비교할 수 있게 함.

### select와 다르게 헷갈렸던 점
- **등록은 한 번, 감시는 계속**: `epoll_ctl(epoll_fd, EPOLL_CTL_ADD, fd, &ev)`로 관심 fd를 등록해두면 끝. select처럼 루프마다 `FD_ZERO`/`FD_SET`을 반복할 필요가 없음. 클라이언트가 새로 붙을 때만 `EPOLL_CTL_ADD`, 나갈 때는 `close()`만 해도 커널이 알아서 감시 목록에서 빼줌(명시적 `EPOLL_CTL_DEL`은 필수는 아니지만 커널 버전에 따라 dup된 fd 등 예외 케이스가 있어 안전하게 직접 해줌).
- **루프 구조 자체가 달라짐**: select는 "전체 클라이언트를 돌면서 `FD_ISSET`으로 준비됐는지 확인"하는 구조였는데, epoll은 `epoll_wait`가 돌려준 이벤트 배열(`n_ready`개)만 그대로 순회하면 됨 → 매칭 안 된 클라이언트, 대기 중인 클라이언트까지 매번 전부 훑을 필요가 없어짐.
- **`ev.data.fd`로 어떤 fd가 준비됐는지 구분**: select의 `FD_ISSET(fd, ...)` 대신, 이벤트 구조체의 `data.fd`(또는 `data.ptr`)로 어떤 소켓이 준비됐는지 알아냄.

### 검증
- 기존 select 버전과 동일한 A/B/C 매칭·relay·재매칭 시나리오를 `server_epoll` + `client` 조합으로 다시 검증하여 동일하게 동작함을 확인.

## 6단계: non-blocking 소켓 + 쓰기 버퍼링 (head-of-line blocking 해결)

### 왜
- 지금까지 `write()`(및 그걸 감싼 `sendMsg`)는 blocking 모드 소켓에 그대로 호출했음. 상대방의 커널 수신 버퍼가 꽉 차면(상대가 느리거나, 읽지 않고 멈춰 있으면) 그 자리에서 `write()`가 블로킹됨.
- 이 서버는 단일 스레드로 모든 클라이언트를 처리하므로, 한 클라이언트에게 보내는 `write()`가 블로킹되면 그동안 다른 모든 클라이언트의 read/write도 같이 멈춰버림(head-of-line blocking). select/epoll로 "읽기 가능"만 감시해왔지, "쓰기가 실제로 안 막히는지"는 신경 쓰지 않았던 셈.

### 설계
- `fcntl(fd, F_SETFL, ... | O_NONBLOCK)`으로 listen_fd와 모든 client_fd를 non-blocking으로 전환.
- fd별로 `map<int, string> outbox`를 두어, `sendMsg()`는 항상 outbox에 먼저 append한 뒤 즉시 flush를 시도. 커널 송신 버퍼가 꽉 차서 `write()`가 `EAGAIN`/`EWOULDBLOCK`을 반환하면 그냥 넘어가고(블로킹하지 않음), 남은 데이터는 outbox에 그대로 둠.
- 아직 못 보낸 데이터가 있는 fd만 다음 루프에서 "쓰기 가능"도 같이 감시: select는 `write_fds`에 추가, epoll은 `epoll_ctl(MOD)`로 `EPOLLOUT`을 등록. 다 보내고 나면 다시 `EPOLLIN`만 남기도록 되돌림(계속 writable 상태인 소켓을 EPOLLOUT으로 감시하면 매번 이벤트가 와서 busy-loop처럼 되기 때문).
- 상대가 데이터를 계속 안 읽어가서 outbox가 무한정 쌓이는 것을 막기 위해 `MAX_OUTBOX_SIZE`(64KB) 상한을 두고, 넘으면 그 연결을 끊음.

### 함정 1: 이벤트 배치 처리 중에 바로 close()하면 안 됨
- 처음엔 read/write 처리 중 상대가 죽은 게 확인되면 그 자리에서 바로 `disconnect()`(= close 포함)를 호출하려 했음.
- 문제: 한 번의 `select()`/`epoll_wait()` 호출이 여러 fd를 동시에 "준비됨"으로 돌려주는 배치 처리 구조인데, 그 배치를 순회하는 도중 어떤 fd를 `close()`해버리면 (a) select 버전은 아직 순회하지 않은 다른 fd를 건드릴 수 있고, (b) epoll 버전은 더 심각하게, OS가 방금 닫은 fd 번호를 바로 그 순간(같은 배치 안에서 `accept()`가 섞여 있으면) 새 연결에 재사용해버려서 이미 처리한 것으로 착각한 이벤트가 엉뚱한 소켓을 가리키게 될 수 있음("stale fd" 문제).
- **해결**: 끊기로 판단된 fd는 즉시 close하지 않고 `vector<int> to_disconnect`에 모아뒀다가, 이번 배치의 이벤트 처리가 전부 끝난 뒤 한 번에 정리. `to_disconnect`가 처리 도중(재매칭 알림 전송 실패 등으로) 더 늘어날 수 있어서 범위 기반 for문이 아니라 `to_disconnect.size()`를 매번 다시 읽는 인덱스 기반 루프로 순회함(그렇지 않으면 벡터가 커지면서 반복자가 무효화될 수 있음).

### 함정 2: 같은 배치에서 매칭 상대 둘이 동시에 끊기면 제3자가 유령 매칭을 겪음
- `/code-review high`로 이번 변경분을 전체 리뷰했을 때 발견됨.
- 시나리오: A-B가 매칭된 상태, C는 혼자 대기 중. A와 B가 (네트워크 문제 등으로) 거의 동시에 연결을 끊어서 같은 `select()`/`epoll_wait()` 배치에 둘 다 "끊김"으로 잡힘.
- `to_disconnect`를 순서대로 처리하면서 A의 `disconnect()`가 먼저 실행되면: B를 대기열에 다시 넣고 `tryMatch()`를 호출 → 마침 C가 대기 중이므로 B와 C가 즉시 재매칭되어 버림(양쪽에 "매칭 성사" 전송). 그런데 바로 다음으로 B의 `disconnect()`가 처리되면서, 방금 맺어진 B-C 매칭을 다시 풀고 C에게 "상대방이 나갔습니다"를 보냄. 결과적으로 C는 실제로 B와 아무 말도 못 해봤는데 "매칭 성사" → "상대방이 나갔습니다"를 순간적으로 둘 다 받는 유령 매칭을 겪음.
- **해결**: `disconnect(fd)`에서 상대(`other_fd`)를 대기열로 되돌리기 전에, `other_fd`가 이번 배치의 `to_disconnect`에도 이미 들어있는지(= 상대도 곧 같이 끊길 예정인지) 확인. 그렇다면 재매칭 알림/재대기열 등록을 건너뛰고 그냥 정리만 함.
- **검증**: A·B(매칭된 쌍)를 거의 동시에 `kill`해서 같은 이벤트 배치에서 함께 끊기도록 유도한 뒤, 대기 중이던 C가 아무 매칭 알림도 받지 않는지 확인 → 이후 새 클라이언트 D가 접속하면 C와 정상적으로 매칭되는 것까지 확인. select/epoll 버전 둘 다 동일하게 통과.

### 함정 3 (함정 2의 사각지대): 재매칭 가드를 "알림을 보내기 전"에만 확인했음
- 7단계(메시지 프레이밍) 작업 뒤 다시 `/code-review high`를 돌렸을 때 발견됨. 함정 2에서 만든 `partnerAlsoLeaving` 가드는 `disconnect(fd)`가 시작되는 시점에 상대(`other_fd`)가 **이미** `to_disconnect`에 들어있는 경우만 잡았음.
- 놓친 경로: 상대에게 "상대방이 나갔습니다" 알림을 보내는 그 `sendMsg(other_fd, ...)` 호출 **도중에** `flushOutbox`가 실패해서 `other_fd`가 그제서야(sendMsg 내부에서) `to_disconnect`에 추가되는 경우. 가드는 이미 통과한 뒤라 그대로 `waiting_queue.push_back(other_fd); tryMatch();`까지 가버려서, 이미 죽은 게 방금 확인된 `other_fd`가 대기 중이던 제3자와 또 순간적으로 재매칭됐다가 곧바로 풀리는 동일한 유령 매칭이 재발함.
- **해결**: `to_disconnect` 확인을 알림을 보내기 **전과 후** 두 번 다 하도록 변경. `sendMsg` 호출 뒤에도 `other_fd`가 `to_disconnect`에 없을 때만 대기열에 되돌리고 `tryMatch()`를 호출함.
- **교훈**: "이 조건은 한 번만 확인하면 충분하다"고 생각했던 가드가, 그 가드 내부에서 호출하는 함수(`sendMsg`)가 같은 종류의 상태 변화(fd를 끊기로 결정)를 스스로 일으킬 수 있다는 걸 놓치면 똑같은 버그가 다른 경로로 재발할 수 있음. 함정 2를 고칠 때도 "여기서만 확인하면 되겠지"라고 짐작하지 말고 "이 값이 이 지점 이후로도 바뀔 수 있는 다른 경로가 있는가"를 계속 의심했어야 함.

### 함정 4 (epoll 전용): EPOLLHUP/EPOLLERR만 뜨고 EPOLLIN은 안 뜨는 경우
- 마찬가지로 재검토에서 발견. 원래(non-blocking 이전) 코드는 listen_fd가 아닌 모든 이벤트에 대해 조건 없이 `read()`를 호출했기 때문에, 상대가 RST로 연결을 끊는 등 어떤 이유로든 그 fd에 문제가 생기면 `read()`가 0이나 에러를 반환해서 자연히 `disconnect()`로 이어졌음.
- non-blocking 전환 과정에서 `if (events[i].events & EPOLLIN)`으로 읽기 처리를 감싸버렸는데, `epoll_wait`는 소켓에 문제가 생기면 `EPOLLIN` 없이 `EPOLLHUP`/`EPOLLERR`만 돌려줄 수도 있음. 이 경우 조건을 통과하지 못해 `read()`를 아예 시도하지 않고, 레벨 트리거 특성상 다음 루프에도 같은 이벤트가 계속 돌아와서 아무 처리도 못 한 채 CPU만 계속 쓰는 busy-loop에 빠짐(그 클라이언트와 상대방 모두 영원히 정리되지 않음).
- **해결**: 읽기 시도 조건을 `events[i].events & (EPOLLIN | EPOLLHUP | EPOLLERR)`로 넓혀서, 이 중 하나라도 뜨면 `read()`를 시도하도록 함 — 어차피 문제가 있는 소켓이면 `read()`가 알아서 0/에러를 반환해 기존 로직대로 정리됨.
- **교훈**: 이벤트 마스크로 분기를 나눌 때, 원래 "무조건 하던 일"을 특정 비트 조건 뒤로 옮기면 그 비트가 안 뜨는 경로가 있는지(HUP/ERR처럼) 반드시 따져봐야 함. select 버전은 애초에 이런 분기가 없어서(그냥 `FD_ISSET`이면 읽기 시도) 이 문제 자체가 없었음.

### 스코프 결정: client.cpp는 그대로 둠
- non-blocking + outbox 버퍼링은 "여러 클라이언트를 한 스레드가 처리하는데 한쪽에 대한 write가 나머지 전체를 막는" 서버 쪽 문제. `client.cpp`는 상대가 서버 하나뿐이라 이 문제가 발생할 여지가 사실상 없어서(내 프로세스만 멈추는 셈) 이번 단계에서는 그대로 blocking write로 남겨둠.

### 검증
- 기존 A/B/C 매칭·relay·재매칭 시나리오를 `server`/`server_epoll` 양쪽 모두에서 다시 통과시킴 (WSL + g++로 컴파일, C++ 클라이언트를 서브프로세스로 stdin에 파이프하는 방식).
- `/code-review high`로 전체 diff 리뷰 → 위 유령 매칭 버그, outbox 무한 증가, `setNonBlocking()` 실패 무시 3건을 실제로 수정 후 재검증. select/epoll 두 파일 사이의 로직 중복은 애초에 "비교 학습" 목적으로 남겨둔 것이라 의도적으로 그대로 둠.
- 메시지 프레이밍(7단계) 작업 뒤 다시 `/code-review high`를 돌려서 함정 3·4를 추가로 발견 및 수정, A·B 동시 종료 유령 매칭 시나리오까지 재검증하여 통과.
- 그 수정분에 대해 다시 한 번 `/code-review high`를 돌린 결과: (1) `server.cpp`에서 write flush 실패로 fd를 `to_disconnect`에 넣고도 그 아래 읽기 처리로 그대로 흘러들어가 죽은 것으로 판단한 소켓에서 데이터를 relay할 수 있는 실제 버그(epoll 버전은 이미 `continue`로 막아뒀던 것과 동일한 문제, select 버전에만 남아있었음) — `continue` 추가로 수정. (2) `sendMsg`가 outbox에 이미 데이터가 쌓여 있어도(=이미 EPOLLOUT 등록됨) 매번 `epoll_ctl(MOD)`를 다시 호출하던 비효율 — append 전 상태를 기억해뒀다가 처음 쌓일 때만 호출하도록 수정. (3) `alreadyLeaving` 체크의 중복된 `find()` 호출을 `isLeaving()` 헬퍼로 정리. select/epoll 두 파일 사이의 큰 틀 중복은 여전히 의도적으로 유지하지만, 이번에 (1)처럼 한쪽에만 반영되고 다른 쪽은 놓치는 drift가 실제로 발생하는 걸 직접 확인함 — 두 파일을 고칠 때는 항상 서로 대조하며 봐야 한다는 교훈.

### 함정 5: 유령 매칭 가드가 놓친 세 번째 경로 — `tryMatch()`가 대기열 자체를 확인하지 않음
- 같은 코드에 대해 다시 `/code-review high`를 돌렸을 때 발견됨. 함정 2/3의 가드는 모두 `disconnect(fd)`가 **상대방(`other_fd`)을 대기열에 되돌리기 직전**에만 확인했음 — `tryMatch()` 자체는 대기열 맨 앞 두 명을 그냥 꺼내 짝짓기만 할 뿐, 그 중 누군가 이미 이번 배치에서 끊기기로 정해져 있는지는 전혀 몰랐음.
- 놓친 경로: Y-Z가 매칭된 상태, X는 혼자 대기 중. Y가 끊기고, **X도 별도의 이유로(읽기 에러 등) 같은 배치에서 끊기기로 정해졌지만 아직 대기열에서 제거되지 않은 채** 남아있는 상황. `disconnect(Y)`가 처리되며 Z를 대기열에 돌려놓고 `tryMatch()`를 부르면, `tryMatch()`는 대기열 맨 앞의 X를 (곧 사라질 걸 모른 채) Z와 그냥 짝지어버림 → Z에게 "매칭 성사" 전송. 곧이어 X 자신의 `disconnect()`가 처리되며 이 매칭을 다시 풀고 Z에게 "상대방이 나갔습니다" 전송 → Z 입장에선 실제로 대화해보지도 못한 X와 유령 매칭.
- **해결**: `tryMatch()` 맨 앞에서 `waiting_queue`를 훑어 이미 `isLeaving()`인 fd를 전부 제거(`remove_if` + `erase`)한 뒤에 짝짓기를 시작하도록 함.
- **검증**: Y-Z를 매칭시키고 X를 혼자 대기시킨 뒤, Y와 X를 거의 동시에 kill → Z가 "매칭 성사"→"상대방이 나갔습니다"만 딱 한 번 받고(X와의 유령 매칭 없이) 이후 새 클라이언트와 정상 재매칭되는 것을 확인. select/epoll 둘 다 통과.
- **흥미로운 추가 관찰**: 이 테스트를 여러 번 반복해보면, Y와 X를 "거의 동시에" kill해도 매번 정확히 같은 `select()`/`epoll_wait()` 배치에 같이 잡히는 건 아니었음 — 어떤 실행에서는 Z가 정상적으로 D와만 재매칭됐고, 다른 실행에서는 Y가 끊기는 시점에 X가 아직 "안 끊긴 것"으로 관측되어(실제로 몇 마이크로초 뒤에 별도 배치로 끊김) Z가 잠깐 X와 정상적으로 재매칭됐다가 X가 끊기며 다시 풀리는 게 관찰됨. 이건 버그가 아니라, 그 순간엔 X가 서버 입장에서 "진짜로 아직 살아있는 걸로 보였던" 것이므로 매 순간의 상태 판단으로는 올바른 동작임. **"동시에"는 정말로 같은 이벤트 배치 안에 들어올 때만 특수 케이스로 다뤄야 하고, 아주 근접한 시간차라도 배치가 갈리면 그건 그냥 "순차적으로 두 번 끊긴 것"으로 취급하는 게 맞다**는 걸 실제로 확인함.

### 함정 6: `disconnect()`가 보내다 만 outbox 데이터를 그냥 버림
- 같은 리뷰에서 함께 발견됨. `disconnect(fd)`는 대기열/매칭 정리 후 바로 `outbox.erase(fd)` + `close(fd)`를 했는데, 그 시점에 `outbox[fd]`에 아직 못 보낸 데이터(예: 상대가 방금 보낸 relay 메시지가 커널 송신 버퍼가 꽉 차서 EAGAIN으로 대기 중이던 것)가 남아있을 수 있음 — 이 fd의 **읽기** 쪽에서 독립적으로 EOF/에러가 나서 `disconnect`가 호출되면, 그 못 보낸 데이터는 재시도 한 번 없이 조용히 사라짐.
- **해결**: `outbox.erase(fd)` 직전에 `flushOutbox(fd)`를 한 번 더 시도(결과는 무시 — 성공하면 좋고, 실패해도 어차피 정리할 것이므로). 상대가 실제로 살아있고 커널 버퍼만 잠깐 꽉 찼던 경우라면 이 마지막 시도로 데이터가 전달될 가능성이 생김.

### 함정 7: 개행 없이 끝난 마지막 메시지가 `disconnect()`에서 조용히 사라짐
- 또 한 번 `/code-review high`를 돌렸을 때 발견(이번엔 앞선 여섯 개의 함정이 실제로 다 제대로 고쳐져 있는지까지 교차 검증한 뒤, 마지막으로 남은 문제로 지적됨).
- 시나리오: 클라이언트가 `"final words"`처럼 개행 없이 마지막 메시지를 보내고 그대로 연결을 끊으면(파이프 입력의 마지막 줄에 개행이 없거나, 네트워크가 끊기는 경우), 그 바이트들은 `inbox[fd]`에 남아있는 채로 `disconnect(fd)`가 `inbox.erase(fd)`를 그냥 호출해버려서 상대에게 전달되지도, 로그도 안 남기고 사라짐.
- **해결**: `disconnect(fd)`에서 상대(`other_fd`) 존재를 확인한 직후, `inbox[fd]`에 아직 남은 내용이 있으면 "연결 종료 자체를 그 메시지의 끝"으로 취급해서 `sendMsg(other_fd, ...)`로 마저 전달한 뒤에 "상대방이 나갔습니다" 알림을 보내도록 순서를 정리함(전달 도중 상대가 죽는 것도 동일하게 재확인). 단, `MAX_LINE_SIZE` 초과로 거부하려던 데이터까지 이 경로를 타면 안 되므로, 그 자리에서 `buf.clear()`로 미리 비워둠.
- **검증**: 매칭된 두 클라이언트 중 한쪽이 개행 없는 문자열만 보내고 곧바로 연결을 끊었을 때, 상대가 그 내용을 한 줄로 받고 이어서 "상대방이 나갔습니다"를 받는 것을 확인. select/epoll 둘 다 통과.
- **테스트 인프라 삽질**: 이 시나리오를 재현하려고 FIFO로 클라이언트 stdin을 붙잡고 있다가 fd를 닫아 EOF를 유도했는데, 처음 두 번은 계속 실패함. 원인은 서버 코드가 아니라 **테스트 스크립트 자체의 파일디스크립터 상속 문제**였음: `exec 3>fifo`로 연 fd를 나중에 닫아도, 그 사이에 새로 띄운 백그라운드 파이프라인(`(printf ...; sleep N) | ./client &`)이 fd 3을 그대로 상속받아 들고 있으면 FIFO의 "쓰기 참조 카운트"가 0이 안 돼서 읽는 쪽이 EOF를 못 받음. 게다가 파이프라인의 왼쪽(`printf ...; sleep N`)과 오른쪽(`./client`)은 각각 별도 서브셸이라 `cmd 3>&-`처럼 오른쪽에만 리다이렉트를 붙여도 왼쪽 서브셸은 여전히 fd를 들고 있음 — `( (좌변) | (우변) ) 3>&-`처럼 파이프 전체를 감싸는 바깥 서브셸에 리다이렉트를 걸어야 양쪽 다 적용됨.

### 함정 8: 개행 없는 마지막 메시지를 relay할 때 개행을 안 붙여서 다음 알림과 한 줄로 붙어버림
- 함정 7을 고친 뒤 다시 `/code-review high`를 돌렸을 때 발견. `disconnect()`가 `inbox[fd]`에 남은 내용을 `sendMsg(other_fd, inboxIt->second)`로 그대로 relay했는데, 그 내용 자체가 애초에 개행이 없어서 inbox에 남아있던 것이므로 그대로 보내면 바로 다음에 보내는 "상대방이 나갔습니다..." 메시지와 개행 없이 이어붙어서 한 줄처럼 보임(`client.cpp`는 받은 바이트를 그대로 화면에 찍기 때문).
- **해결**: relay할 때 `inboxIt->second + "\n"`으로 개행을 붙여서 독립된 한 줄로 도착하게 함.

## 7단계: 메시지 프레이밍 (개행 기준 재조립)

### 왜
- TCP는 바이트 스트림이라 `read()` 한 번이 상대가 보낸 "한 메시지"와 일치한다는 보장이 없음. 지금까지는 `read()`로 받은 바이트를 그대로(어디서 잘렸든) relay했는데, 사람이 터미널에서 한 줄씩 타이핑해서 보내는 지금 테스트 환경에서는 거의 항상 한 줄이 한 번의 `read()`/`write()`로 들어맞아서 문제가 드러나지 않았을 뿐임. 나중에 이동/공격 같은 구조화된 명령을 다루려면 메시지 경계를 스스로 관리해야 함.

### 설계
- fd별 `map<int, string> inbox`를 두어 `read()`로 받은 바이트를 계속 append.
- `inbox[fd]`에서 개행(`'\n'`)을 찾아서 나올 때마다 그 앞부분(개행 포함)을 "완성된 한 메시지"로 잘라내어 relay하고, 나머지는 inbox에 그대로 남겨 다음 `read()`와 이어붙임. 한 번의 `read()`에 여러 줄이 몰려 들어와도 while 루프로 전부 잘라냄.
- 개행 없이 한없이 긴 데이터가 들어오는 것을 막기 위해 `MAX_LINE_SIZE`(64KB) 상한을 두고 넘으면 연결을 끊음(outbox와 동일한 이유의 backpressure).
- 더 이상 `buffer`를 C 문자열처럼 다루지 않으므로(항상 `n` 길이만큼만 `append`) `read()`에 `sizeof(buffer)-1` 대신 `sizeof(buffer)`를 그대로 넘기고, `buffer[n]='\0'`도 제거함 — 1단계 노트에 적었던 "널 종료 보장 안 됨" 문제 자체가 애초에 필요 없어짐.

### 검증
- 한 클라이언트가 개행 없이 "partial-"만 먼저 보내고 잠깐 뒤에 "message\n"을 마저 보내는 상황을 만들어서, 첫 조각만으로는 상대방에게 아무것도 relay되지 않고(아직 완성된 줄이 아니므로) 개행이 도착한 뒤에야 "partial-message" 한 줄이 통째로 relay되는 것을 확인.
- 기존 A/B/C 매칭·relay·재매칭 시나리오와 함정 2의 동시-종료 유령 매칭 회귀 테스트를 다시 통과시켜 프레이밍 도입이 기존 동작을 깨지 않았음을 확인. select/epoll 두 버전 모두 통과.
- `client.cpp`는 변경하지 않음: 보내는 쪽은 사용자가 엔터를 눌러야 전송되는 구조라 이미 항상 개행으로 끝나고, 받는 쪽은 화면에 그대로 찍기만 해서 프레이밍을 직접 파싱할 필요가 없음.
